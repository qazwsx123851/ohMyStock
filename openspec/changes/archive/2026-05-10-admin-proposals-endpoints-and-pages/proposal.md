## Why

`proposal-state-machine` (archived 2026-05-10) shipped `transition_proposal()` and the 5 legal edges (`pending→validating→{approved,rejected}`, `approved→{merged,rejected}`); `proposal-writer` (archived 2026-05-10) ships the markdown writer that the Phase 5 review pipeline already calls. The closed-loop self-improvement cycle is therefore mechanically complete on the backend — but to actually use it today, Mark has to `cat proposals/PENDING_REVIEW/<date>-<topic>.md`, then drop into a Python REPL and call `transition_proposal(path, "approved", actor=..., validation_report_path=...)` by hand. `web-admin` already exposes `/proposals` and `/proposals/:slug` as `ComingSoon` stubs (`web-admin/src/pages/stubs.tsx`); the page-designs SSOT (`docs/web-admin-page-designs.md`) has reserved these slots since v3 design.

We ship a **read + transition v0**: list every proposal across `proposals/{root,PENDING_REVIEW,merged,rejected}/`, render one's full frontmatter + 7-section body + changelog, and expose a single `[Transition]` button row whose options are filtered by `current_status` so only the legal edges are clickable. No WFA engine, no auto-validation, no git/PR automation, no cheatsheet diff application — those stay explicitly deferred to later changes (`wfa-validation-engine`, etc.). This change closes the human-in-the-loop step of the self-improvement cycle without inventing logic that does not yet exist.

## What Changes

- New `GET /api/admin/proposals` endpoint: walks `proposals/{root,PENDING_REVIEW,merged,rejected}/` (skipping the 4 status sub-dirs at root) and returns parsed frontmatter only (no body) for each file, sorted by `created_at DESC`. Optional `?status=` query param (one of the 5 `ProposalStatus` values) for server-side filter. Paginated `{items,total,limit,offset,has_more}` matching the memory/skills shape; `limit` clamps to ≤200, `offset≥0`. No body / changelog leakage on the list endpoint.
- New `GET /api/admin/proposals/{slug}` endpoint: returns full `frontmatter` + 7 body sections + parsed `changelog` (each `## 8.` entry as `{timestamp, from_status, to_status, actor, reason?}`). 404 envelope (`code: "not_found"`) when no file matches. 400 (`code: "invalid_input"`) for path-traversal-style slugs. `slug` is the filename stem without `.md` (e.g. `2026-05-12-tighten-rs-percentile-floor`).
- New `POST /api/admin/proposals/{slug}/transition` endpoint: thin wrapper over `transition_proposal()`. Body `{new_status, actor, reason?, validation_report_path?, merged_to_version?}`. Maps `ProposalStateError` codes 1:1 to `{ok:false, error:{code, message}}`: `unknown_status`/`illegal_transition`/`missing_actor`/`missing_validation_report_path`/`missing_merged_to_version`/`missing_reason`/`destination_exists`/`malformed_changelog` → 400 (or 409 for `destination_exists`). 200 returns `{slug, new_status, new_path}` on success.
- New `ProposalsPage` (`/proposals`): replaces the stub. Segmented filter (all / pending / validating / approved / merged / rejected) drives `?status=` on the list call. `<DataTable>` with 5 columns (`created_at` / `status` badge / `topic` / `target_section` / `priority`); status badge uses `<CategoryBadge>`-style neutral chip (no 紅漲綠跌 — proposals carry no price semantic). Click row → `/proposals/<slug>`. No SSE.
- New `ProposalDetailPage` (`/proposals/:slug`): replaces the stub. Header (back-link + h1 + status badge + priority badge + `created_by` + `created_at`); 7 sections rendered as `<pre className="whitespace-pre-wrap">` blocks (no markdown parser, consistent with `/skills/:name`). Changelog rendered as a chronological list. **Action row** at the bottom whose buttons are derived from `current_status` and the 5 legal edges only — anything else is `disabled` or hidden. Buttons open a modal that collects required args (`actor` always; `validation_report_path` for `approved`; `merged_to_version` for `merged`; `reason` for `rejected`); on submit calls the transition endpoint, on success refetches detail. Errors render the envelope `code` + `message` inline, no retry.
- Extend `web-admin/src/lib/api.ts` with `Proposal` / `ProposalDetail` / `ProposalChangelogEntry` / `ProposalStatus` types + `listProposals(status?, limit?, offset?)` / `getProposal(slug)` / `transitionProposal(slug, body)` wrappers.
- Update `docs/web-admin-page-designs.md` `/proposals` and `/proposals/:slug` rows to mark v0 scope (note WFA gate, auto-validation, git/PR automation remain deferred).
- Add CLAUDE.md §5 SSOT rows pointing at the two new specs + the endpoint file.

Out of scope (deferred, explicitly): WFA validation engine that produces the report `validation_report_path` points to; auto-run scheduling; git commit / PR automation on `merged`; cheatsheet diff application; EventBus `proposal_transitioned` event type; markdown renderer for body; full-text search across proposals; bulk-transition UI; `reverted_at` rollback flow.

## Capabilities

### New Capabilities
- `admin-proposals-endpoints`: `GET /api/admin/proposals` (paginated list, frontmatter only, optional `?status=` filter), `GET /api/admin/proposals/{slug}` (full body + parsed changelog), `POST /api/admin/proposals/{slug}/transition` (thin wrapper around `transition_proposal()` with `ProposalStateError`→envelope mapping). All Bearer-auth, unified `{ok,data,error}` envelope, per-request DB conn (consistent with all other admin routes).
- `web-admin-proposals-pages`: `/proposals` route + `/proposals/:slug` route — replacing the existing `ProposalsPage` / `ProposalDetailPage` stubs in `pages/stubs.tsx`. Status-filter list, body+changelog detail, and a status-aware transition action row backed by a small modal.

### Modified Capabilities
- (none — both routes are stub-replacements; `proposal-state-machine` and `proposal-writer` capabilities are consumed unchanged.)

## Impact

- **Code**: new `src/ohmystock/api/routes/proposals.py` + register in `api/app.py`; new `web-admin/src/pages/ProposalsPage.tsx` and `web-admin/src/pages/ProposalDetailPage.tsx`; remove `ProposalsPage` / `ProposalDetailPage` from `web-admin/src/pages/stubs.tsx`; update `web-admin/src/router.tsx` imports; extend `web-admin/src/lib/api.ts` with `listProposals` / `getProposal` / `transitionProposal` + types; tests for endpoint (FastAPI `TestClient` against a tmp `proposals/` dir) + pages (RTL with mocked fetcher); CLAUDE.md §5 rows + a small note in `docs/web-admin-page-designs.md`.
- **APIs**: 2 new GET endpoints + 1 new POST endpoint. No schema migrations (proposals are filesystem-backed). No SSE event types added.
- **Dependencies**: none new. Reuses already-installed `pydantic`, `react-query`, shadcn primitives, and the existing `transition_proposal()` / `parse_proposal()` helpers from `src/ohmystock/proposal/`.
- **Security**: slug validation reuses the same hardening pattern as `admin-skills-endpoints` — reject `/`, `\`, `..`, `os.sep` BEFORE filesystem access (`code: "invalid_input"` 400). The transition endpoint is the only mutating admin endpoint that touches the working tree outside of SQLite; it is constrained to the 5 legal edges enforced inside `transition_proposal()`, and `actor` must come from the request body (never inferred from the Bearer token, since the token is shared and the actor is a free-form audit field). No secrets are ever serialised — proposal frontmatter is public source.
- **Risk**: low–medium. Read-only on `proposals/` for the two GETs; the POST renames files between sub-directories and appends one line to `## 8. 變更紀錄`, atomically via `os.replace` (already shipped in `proposal-state-machine`). Misuse-worst-case is a malformed transition that the state machine already rejects with `illegal_transition` before any I/O. No broker behaviour change, no breaker change, no `OHMYSTOCK_AUTO_EXECUTE` interaction.
